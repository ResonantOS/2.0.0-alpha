# Support

## Public Intake

Use GitHub Issues for public, actionable intake:

- [Report a bug](https://github.com/ResonantOS/2.0.0-alpha/issues/new?template=bug.yml)
- [Request a feature](https://github.com/ResonantOS/2.0.0-alpha/issues/new?template=feature.yml)
- [Search existing issues](https://github.com/ResonantOS/2.0.0-alpha/issues)

Issues are the public intake queue. [Project 2](https://github.com/orgs/ResonantOS/projects/2)
is the release-planning source of truth; an issue's requested scope is not a
release commitment. See [Project Governance](docs/PROJECT_GOVERNANCE.md) for
triage and promotion rules.

The alpha supports the Chrome Manifest V3 extension and local Node.js bridge.
Before filing a bug, reproduce it from the latest relevant `dev` commit and
check the setup instructions in [README.md](README.md).

## Protect Private Data

Never put secrets or sensitive personal data in an issue, pull request,
comment, attachment, screenshot, or log. This includes API keys, access tokens,
cookies, wallet credentials, browser profiles, login databases, generated
bridge tokens, private prompts, and provider payloads.

Use minimal test data and redact diagnostics. If a report cannot be made public
safely, do not create an issue. Suspected vulnerabilities must follow the
private process in [SECURITY.md](SECURITY.md). Sensitive conduct reports must
follow [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).

## What To Expect

Maintainers triage reports on a best-effort basis. A complete reproduction and
clear expected behavior make a report easier to act on. Maintainers may close
duplicates, unsupported-environment reports, requests without enough
information, or questions already answered by current documentation.

There is no private product-support channel or guaranteed response time for the
alpha. Security response targets are defined separately in `SECURITY.md`.
